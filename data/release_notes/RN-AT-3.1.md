# Atlas SD-WAN release 3.1: release notes

## Overview
Atlas SD-WAN 3.1 adds controls for route-cache aging, migration handling for LTE profiles during upgrade, and configurable reporting retention. The release also includes stability work in the orchestrator policy pipeline and certificate validation path, with a specific fix for policy pushes that could hang on large route-maps and a fix for stale CRL data blocking policy distribution. Operators should review route-cache and reporting defaults before upgrade, and validate LTE transport settings after any edge conversion or migration. The main operational focus in 3.1 is preserving existing forwarding behaviour while making cache lifetime, LTE profile migration, and report storage more predictable.

## New features
### Route-cache aging controls
This release introduces configuration for route-cache aging so administrators can control how long learned routes remain eligible for application-aware routing decisions. The setting applies to overlay route selection on the edge and is intended to reduce stale path use in environments with frequent route changes. Review existing app-route policies and cache-dependent failover behaviour before enabling a shorter aging interval.

### Upgrade migration for LTE profiles
Atlas SD-WAN 3.1 adds upgrade-time migration for LTE transport profiles to preserve cellular configuration across the 3.0 to 3.1 transition. The orchestrator maps existing LTE profile parameters into the new schema during edge upgrade so that transport settings remain consistent after the device rejoins the overlay. After upgrade, verify interface state and tunnel parameters on edges that use LTE as a primary or backup transport.

### Reporting retention configuration
This release adds configurable retention for reporting data generated by the orchestrator. Administrators can set how long telemetry and report records are kept before automatic cleanup, which helps align storage use with operational and compliance requirements. Existing reporting jobs continue to run, but retention changes affect how long historical data remains available in dashboards and exports.

## Resolved issues
- KB-5103: Atlas SD-WAN 3.0: policy push hangs when a route-map contains more than 256 entries (ERR-ORCH-4412)
- KB-5111: Atlas SD-WAN 2.9: orchestrator blocks policy push when the CRL update is older than 24 hours (%PKI-4-CRL-EXPIRED)

## Known issues
- KB-5104: Atlas SD-WAN 3.1: upgrade rewrites LTE tunnel MTU to 1500 on dual-SIM edges. Workaround: After the upgrade, manually reapply the tunnel MTU on each LTE interface and verify that the configured value matches the pre-upgrade setting. Use 1400 to 1420 bytes for most carrier LTE links, and retest with 1472-byte pings before returning the site to service.
- KB-5109: Atlas SD-WAN 3.1: app-aware routing keeps using a withdrawn route until the cache ages out. Workaround: Trigger a route-refresh after any planned underlay withdrawal, or shorten the route-cache timer to 60 seconds during maintenance windows. Confirm that the stale candidate disappears before changing traffic to the backup link.

## Compatibility
Atlas SD-WAN 3.1 supports upgrade from 3.0; direct upgrade from earlier major.minor trains is not supported unless the site is first brought to 3.0. The release is compatible with supported Atlas orchestrator deployments and edge hardware from the 3.0 family, including dual-SIM LTE edges, provided the device model is listed as upgrade-supported in the management inventory. Configuration is retained across upgrade in most cases, but LTE profile migration and route-cache aging introduce new defaults that should be reviewed after deployment. Interoperability with existing overlay tunnels, SLA classes, certificate-based control-plane authentication, and reporting integrations is maintained, although sites with strict CRL handling should confirm certificate refresh and policy push health before broad rollout.

## Upgrade notes
Supported direct upgrade path from 3.0. Back up the configuration before upgrading and review the known issues above.

1. Back up the orchestrator configuration, edge inventory, and reporting settings, and export any custom policy objects before starting the upgrade.
2. Verify the 3.1 images for the orchestrator and all target edge models, and confirm available storage on the orchestrator and remote edges.
3. Schedule a maintenance window long enough to upgrade the orchestrator first, then perform a staged edge rollout by site or transport group.
4. Upgrade the orchestrator to 3.1, allow policy and certificate services to return to steady state, and confirm that policy push completes successfully.
5. Upgrade a small set of representative edges, then check tunnel status, LTE profile migration, and app-aware routing with commands such as show sdwan tunnels and show app-route sla-class.
6. After the rollout, validate reporting retention settings, review logs for policy push or certificate warnings, and confirm that withdrawn-route behaviour and LTE MTU values match the intended configuration.
