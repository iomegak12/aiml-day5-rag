# KB-2101: Aurora AR-900 9.1.4 and 9.1.6 BGP IPv4 next-hop stays unresolved after underlay route withdrawal

## Summary
On Aurora AR-900 release 9.1.4 and 9.1.6, eBGP IPv4 routes can remain installed in the BGP table with a valid AS path while the selected next hop is shown as unresolved after an underlay route flap. The BGP session remains Established, but the affected prefixes are not installed in the routing table until recursion is forced to run again.

## Symptoms
This issue is usually seen after a connected or static underlay route is withdrawn and then relearned within a short interval, commonly after a track event or interface flap. Within about 5 to 10 seconds, 50 to 200 eBGP IPv4 prefixes may stop appearing in `show ip route bgp` even though `show bgp summary` still shows the peer as Established and the prefixes are still present in the BGP table with a valid AS path.

Operators typically observe that the route selection state shows the next hop as unresolved or not resolvable. The condition persists until BGP is cleared for the affected address family or the underlay route is removed and re-added so recursion is recomputed.

## Diagnosis
1. Run `show bgp summary` and confirm the affected neighbor remains in the Established state. If the session is up but routes are missing from the RIB, continue.
2. Run `show bgp ipv4 unicast` for one of the missing prefixes and verify that the route is present in BGP with a valid AS path but the next-hop state is unresolved.
3. Run `show ip route bgp` and confirm that the affected prefixes are absent from the installed routing table even though BGP still lists them.
4. Run `show ip route 198.51.100.0/24` or the relevant underlay prefix and verify that the resolving connected/static route was recently withdrawn and relearned.
5. If available, run `debug bgp recursion` during the flap window and look for a negative recursion entry that is not cleared after the underlay route returns. A matching `%BGP-4-NH-RESOLVE` event confirms the condition.
6. Check `show bgp ipv4 unicast neighbors <peer> advertised-routes` or the equivalent peer view to confirm the session continues to exchange updates while only the recursion state is stale.

## Root cause
In the 9.1 family, the BGP next-hop recursion cache can retain a stale negative resolution entry when the route used to resolve the next hop is withdrawn and relearned within the 30-second hold interval. In that state, the BGP session stays up and the best-path remains valid, but the recursion engine does not retry resolution immediately.

As a result, the affected prefixes remain present in BGP but are not programmed into the routing table until another incremental update occurs or the recursion state is forced to refresh manually.

## Workaround
1. If the affected path is critical, schedule a maintenance window and clear the BGP process for the affected IPv4 unicast address family to force next-hop recursion to be rebuilt.
2. If you prefer to avoid a BGP clear, remove and re-add the underlay resolving route so the recursion engine recomputes the next hop. This is most effective when the route can be flapped cleanly without traffic impact.
3. For short-term protection during the maintenance window, use a static discard route with a lower distance than the learned underlay so the resolving path remains stable while the change is made.

```text
clear bgp ipv4 unicast 65001
clear ip route 198.51.100.0/24
```

## Resolution
The defect is fixed in release 9.2.0. In that release and later, BGP invalidates the next-hop recursion cache whenever the resolving route changes state, so withdrawn and relearned underlay routes no longer leave eBGP IPv4 prefixes stuck in an unresolved state.
