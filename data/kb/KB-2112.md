# KB-2112: Aurora AR-900 9.2.3 control-plane protection may miss IPv6 ND drops during traffic bursts

## Summary
Aurora AR-900 running 9.2.3 can underreport dropped IPv6 neighbor discovery (ND) traffic in the control-plane protection statistics during short traffic bursts. In affected cases, the control-plane receives more IPv6 ND punts than the configured policer should allow, but the drop counter remains unchanged for short intervals.

## Symptoms
On 9.2.3, a burst of IPv6 neighbor discovery traffic can push the control-plane above the configured limit while the drop counter remains unchanged. In the cases observed, `show control-plane protection statistics` held at 0 drops for 30-60 seconds, CPU usage climbed from 15% to 85%, and IPv6 neighbors would periodically move to Stale. The issue is most apparent when 5,000-8,000 NS/NA packets arrive in short bursts from a single access VLAN.

Operators typically report intermittent neighbor churn on a single VLAN or access segment, while other forwarding functions continue to work. The event is usually correlated with a temporary rise in control-plane CPU and a lack of corresponding increments in the IPv6 ND drop counters.

## Diagnosis
1. Run `show control-plane protection statistics` and confirm that IPv6 ND input is near or above the configured policer rate while the drop counter remains at 0 or does not increment during the burst.
2. Run `show process cpu` and look for control-plane CPU rising sharply, commonly from normal idle values near 15% to sustained values above 80% while the event is active.
3. Run `show ipv6 neighbors` and check for entries on the affected VLAN moving from Reachable to Stale in a periodic pattern.
4. Run `show logging` and look for `ERR-CPP-4412` messages that align with the same timestamps as the traffic burst.
5. If packet capture is available on the access interface, confirm a short burst of approximately 5,000-8,000 NS/NA packets sourced from one access VLAN within a few seconds.
6. If the burst repeats, compare `show control-plane protection statistics` before and after the event; affected systems show traffic growth without matching drop counter movement.

## Root cause
The punt policer tracks IPv6 ND packets in a 32-bit per-queue counter that is sampled every 250 ms. When traffic arrives in bursts, the counter can wrap between samples, and the excess packets do not take the drop decision path. As a result, the CPU receives more traffic than the intended policer rate permits.

This is a control-plane accounting defect rather than a forwarding-plane failure. The policer configuration remains present, but under the burst conditions described above the drop accounting can lag or remain at zero until the burst subsides.

## Workaround
1. Reduce IPv6 ND load at the edge by applying RA guard or storm control on the access VLAN to limit unsolicited neighbor discovery bursts.
2. Temporarily lower the control-plane policer to a conservative value so that the CPU is protected while the source is isolated; the recommended interim value is 2,000 pps.
3. If the burst persists on a specific access port, shut that port for about 30 seconds to allow neighbor state to recover and to stop the punt surge.
4. After the traffic source is isolated, restore normal edge policy only after control-plane CPU and neighbor state have stabilized.

```text
configure
control-plane
police ipv6-nd 2000
```

## Resolution
The defect is fixed in release 9.3.0. Aurora AR-900 9.3.0 uses lossless accounting for IPv6 ND punts in control-plane protection, so burst traffic is correctly sampled and dropped according to the configured policer.
