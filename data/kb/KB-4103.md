# KB-4103: Orion OW-20 4.8 AP join stalls when the second capability exchange is delayed

## Summary
On Orion OW-20 release 4.8, APs can remain in the joining state for several minutes and then restart the CAPWAP session before authorization completes. The issue is typically seen on higher-latency branches or links with brief loss bursts during the join exchange.

## Symptoms
Affected APs appear in `joining` for 2 to 4 minutes and never transition to `authorized`. In `show ap summary`, the `join pending` count increases as additional APs stall, while the join retry counter increments twice and then stops. The AP remains reachable from the controller, but the join state does not advance, and the controller eventually abandons the session.

The condition is more visible when RTT is approximately 60 to 100 ms and the uplink experiences short retransmit bursts during registration. Operators may see repeated join attempts without a successful handoff into the authorized state, even though the AP does not fully lose connectivity.

## Diagnosis
1. Run `show ap summary` and confirm one or more APs are listed in `join pending` while the AP state remains `joining` for longer than expected.
2. Check `show logging last 50` for `ERR-APJ-4417` entries or repeated join retry messages followed by session teardown. The presence of a retry count that increments twice and then stops is consistent with this issue.
3. If available, run `show client detail <mac>` for a client associated to the AP after a successful retry path; stalled APs usually show no client activity because the AP never reaches authorized operation.
4. Verify the branch link conditions during the join window. If RTT is consistently in the 60 to 100 ms range and packet loss briefly exceeds 0.5%, the join stall is more likely to occur.
5. Confirm the controller release with `show version` or the equivalent system status display. The defect is specific to 4.8 and is not expected on fixed releases.
6. If join failure correlates with delayed capability exchange responses rather than AP hardware faults, treat the issue as a controller join-path defect rather than an AP-specific failure.

## Root cause
The 4.8 join path waits for the second capability exchange on a separate worker thread. Under retransmit pressure, that worker can be pre-empted by the join retransmit timer, which prevents the session from being re-armed correctly. When the delayed capability response finally arrives, the controller has already moved the join context into an orphaned state, so processing does not resume and the AP is forced to restart CAPWAP registration.

This is a controller-side defect in the join state machine. The AP is still reachable on the network, but the controller no longer owns a valid active join session for that AP, so the registration cannot complete.

## Workaround
1. Increase the join timeout to 180 seconds so the delayed capability exchange has time to complete before the session ages out.
2. Keep AP uplink loss below 0.5% during the initial join window; if the branch circuit is unstable, postpone registration until the link is clean.
3. If possible, stage the APs locally on a stable access segment, allow them to complete their first registration there, and then move them to the branch site after they are authorized.
4. Monitor the controller logs after the change and confirm that join retries stop increasing and that APs move from `joining` to `authorized`.

```text
show ap summary
ap join timeout 180
show logging last 50
```

## Resolution
The defect is fixed in release 4.9. In that release, delayed capability responses are matched to the active join session before the session can age out, preventing the orphaned join state and allowing APs to complete authorization normally.
