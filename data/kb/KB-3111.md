# KB-3111: Nimbus NF-300 5.1.3 and 5.1.5: upgrade from 5.0.x may reset configuration objects if checkpoint replay exceeds 4,096 entries

## Summary
On Nimbus NF-300 systems upgraded from 5.0.x to 5.1.3 or 5.1.5, the upgrade may complete without an error, but part of the configuration is not restored into the runtime database. This issue is associated with large checkpoint replay sets and affects systems with heavy policy/object counts.

## Symptoms
After the first login following an upgrade from 5.0.x to 5.1.3 or 5.1.5, customers may find that selected configuration objects are missing. In typical cases, 50 to 200 policy entries are absent, while `show running-config` displays default values in places where custom objects, rules, or profiles previously existed.

The boot process itself usually finishes successfully, and the device may pass basic health checks. The failure is discovered only when comparing pre-upgrade and post-upgrade configuration state, or when services dependent on the missing objects behave as if the configuration had been reset.

## Diagnosis
1. Run `show configuration checkpoint summary` and confirm whether the system contains a checkpoint set larger than 4,096 entries. Large checkpoint counts increase the likelihood of replay cursor loss during upgrade.
2. Run `show running-config` immediately after the first post-upgrade login. If policy objects, rules, or custom profiles are replaced by defaults, the runtime database did not fully receive the replayed configuration.
3. Run `show session table summary` and verify that the active session count is not directly related to the missing objects. This issue is configuration replay related, not a session-table exhaustion condition.
4. Check upgrade logs for the replay cursor message. Presence of `%UPGRADE-4-REPLAY_CURSOR` indicates the migration engine lost its position after a full batch and did not commit later batches into runtime state.
5. If available in your maintenance workflow, review the pre-upgrade backup created before the upgrade and compare object counts against the post-upgrade configuration. A mismatch of roughly 50 to 200 policy entries is consistent with this defect.

Example output:

```text
2026-03-14T02:13:07Z %UPGRADE-4-REPLAY_CURSOR: migration replay cursor lost after batch 1 of 4096 entries; remaining checkpoint batches accepted but not committed
```

## Root cause
The migration engine replays configuration checkpoints in 4,096-entry batches. On upgrades to 5.1.3 or 5.1.5, if the destination schema introduces a new object type, the replay cursor can be lost after the first full batch. Subsequent batches are accepted by the upgrade process but are not committed to the runtime database.

As a result, the appliance boots successfully, but only a portion of the intended configuration is present after the first login. The missing objects appear as defaults or absent entries in the running configuration even though the checkpoint data was processed during upgrade.

## Workaround
1. Before upgrading, reduce the size of the configuration checkpoint so each replay set remains under 4,000 entries. If the deployment is large, split policy objects into smaller groups and validate that each exported checkpoint stays below the threshold.
2. Create a verified backup of the current running configuration to external storage before starting the upgrade. Use the pre-upgrade backup location shown in the command output generated by the standard workflow.
3. Upgrade the system, then log in immediately after reboot and compare the running configuration against the saved backup. If objects are missing, re-import the policy objects from the backup or rebuild the missing sections from the saved configuration.
4. For large environments, verify object counts and critical policy sections before returning traffic to production. Do not assume the upgrade is complete solely because the boot process finished without errors.

```text
show configuration checkpoint summary
copy running-config backup://198.51.100.20/nf300-preupgrade.cfg
```

## Resolution
The defect is fixed in release 5.2.0. In 5.2.0 and later, replay cursor state is preserved across all checkpoint batches, preventing partial configuration reset during upgrade from 5.0.x.
