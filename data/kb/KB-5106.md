# KB-5106: Atlas SD-WAN 3.2: IPSec tunnel negotiation fails with peers that require AES-GCM and SHA-384 on the same proposal

## Summary
Atlas SD-WAN 3.2 can fail to establish an IPSec tunnel when the remote peer requires a single ESP proposal that includes both AES-GCM encryption and SHA-384 integrity attributes. In this case, the Atlas edge continues to retry negotiation but never reaches an established state. The issue is limited to 3.2 and is corrected in 3.3.

## Symptoms
Affected sites remain in tunnel negotiation and do not transition to established. On the edge, the tunnel state stays at negotiating and the retry interval remains at 10 seconds. Traffic over the overlay is unavailable for that peer, while other tunnels may remain healthy.

The failure is seen only with peers that insist on a combined ESP proposal form. If the remote device accepts separate integrity and encryption proposals, or if the peer policy allows alternate transforms, the tunnel may establish normally. The event is typically visible in system logs as a proposal mismatch during IKE negotiation.

## Diagnosis
1. Run `show sdwan tunnels` on the affected edge and confirm the tunnel state remains negotiating rather than established. Look for repeated retries and no successful SA creation.
2. Check the edge logs for IKE negotiation errors. The presence of `%IKE-3-PROPOSAL-MISMATCH` indicates the remote peer rejected the offered transform set.
3. Run `show app-route sla-class` only if application-aware routing is involved to confirm the issue is not caused by SLA classification or path selection. Healthy SLA results with a stuck tunnel point back to IPSec negotiation.
4. If available, inspect the peer-side IKE/IPSec logs and verify that the peer policy requires a single ESP proposal containing both encryption and integrity attributes. A reject reason tied to transform format confirms this interoperability issue.
5. Validate the configured proposal on the Atlas edge and confirm it is using AES-GCM. In 3.2, the negotiator may advertise AES-GCM as encryption-only when the peer expects a combined proposal form.

Example output:

```text
2026-03-14T02:13:07Z edge01 %IKE-3-PROPOSAL-MISMATCH: peer 198.51.100.24 rejected transform set aes-gcm-256;sha384, combined esp proposal required
2026-03-14T02:13:07Z edge01 %IKE-6-RETRY: retrying ike sa negotiation in 10 seconds
2026-03-14T02:13:17Z edge01 %IKE-3-PROPOSAL-MISMATCH: peer 198.51.100.24 rejected transform set aes-gcm-256;sha384, combined esp proposal required

edge01# show sdwan tunnels
peer              local-if   state        uptime   encap
198.51.100.24     wan0       negotiating  00:00:00 ipsec

edge01# show sdwan tunnels detail
peer 198.51.100.24
  ike state: negotiating
  child sa: not installed
  last proposal: aes-gcm-256 / sha384
  retry timer: 10s
```

## Root cause
In Atlas SD-WAN 3.2, the IPSec negotiator advertises AES-GCM as an encryption-only suite when the remote peer requests a single proposal that carries both encryption and integrity fields. AES-GCM is cryptographically valid for ESP, but some peers enforce the proposal structure defined in their local policy and will reject a proposal that does not match that combined form.

As a result, IKE negotiation never completes even though the primitives themselves are compatible. This is an interoperability defect in proposal formatting, not a certificate, routing, or transport failure.

## Workaround
1. Modify the remote peer policy so it accepts an AES-GCM proposal without a separate integrity field, or select an alternate transform such as AES-CBC with SHA-384 if the peer allows it.
2. Apply the Atlas-side proposal change to match the peer policy. Use the documented tunnel proposal command on the affected edge, then commit the configuration.
3. Confirm that both peers now show the same negotiated ESP proposal and that the child SA is installed.
4. Verify `show sdwan tunnels` reports the tunnel as established and that traffic passes across the overlay before returning the site to service.

```text
tunnel ipsec proposal set aes-gcm-256 sha384
commit
```

## Resolution
This defect is fixed in release 3.3. In 3.3, the negotiator emits a combined ESP proposal when required by the peer, allowing tunnels to establish with devices that mandate AES-GCM and SHA-384 in the same proposal.
