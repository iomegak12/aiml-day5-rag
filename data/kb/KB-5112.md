# KB-5112: Atlas SD-WAN 3.3: edge CPU spikes during LTE handoff when both modems are enabled

## Summary
In Atlas SD-WAN 3.3, dual-modem edges can experience a transient control-plane CPU spike during LTE handoff. The condition is most visible when the handoff overlaps a policy refresh, causing short-lived overlay degradation and delayed tunnel keepalives.

## Symptoms
On affected 3.3 edges with both LTE modems enabled, a handoff can drive control-plane CPU to 95 to 100 percent for approximately 15 to 30 seconds. During the spike, tunnel keepalives may be delayed, overlay status may briefly report degraded, and application routing updates can appear to lag until the control plane recovers.

The condition is typically limited to dual-modem deployments. Single-modem edges do not exhibit the CPU spike, and the event is usually self-clearing once the handoff completes and the control plane drains the excess work queue.

## Diagnosis
1. Run `show system cpu` during or immediately after the LTE handoff. CPU pinned in the 95 to 100 percent range on the control-plane process, with no sustained dataplane saturation, supports this issue.
2. Run `show sdwan tunnels`. Look for tunnels in `degraded` or `down` state with keepalive jitter or missed probe counters increasing during the handoff window.
3. Run `show app-route sla-class`. If policy refresh coincides with the event, expect delayed class recomputation or stale transport preference entries while the control plane is busy.
4. Run `show log | include ERR-LTE-2201`. The presence of this message during modem state changes confirms the LTE manager detected the handoff condition that triggers the spike.
5. If available, run `show lte state` or `show lte modem detail`. Verify that both modems are enabled and that the active/standby roles changed within the same interval as the CPU spike.

## Root cause
In 3.3, the LTE manager handles both modem state machines synchronously during a handoff. When both modems are enabled, each link-state notification can trigger a reevaluation of the same transport profile, and the duplicate notifications create unnecessary control-plane work.

That burst of repeated evaluation starves tunnel maintenance timers long enough for keepalives to slip and overlay health to report transient degradation. The behavior is specific to dual-modem handoffs and is amplified when a policy refresh occurs at the same time.

## Workaround
1. Reduce handoff churn on dual-modem edges by applying a debounce interval to the LTE interface so transient signal loss does not trigger rapid modem oscillation.
2. If operationally required, perform the change during a maintenance window and avoid concurrent policy pushes or other orchestrator refresh activity while the carrier switchover is in progress.
3. After the debounce is in place, verify that subsequent handoffs no longer drive sustained control-plane CPU above normal operating levels and that tunnel keepalives remain stable.

```text
interface lte0 handoff-debounce 5000
commit
```

## Resolution
No software fix is required for this issue. Prevent recurrence by dampening LTE handoff events on 3.3 dual-modem edges, using the recommended debounce setting and avoiding policy pushes during carrier switchover windows. Where possible, keep only one modem enabled during planned maintenance to eliminate the duplicate notification burst that triggers the CPU spike.
