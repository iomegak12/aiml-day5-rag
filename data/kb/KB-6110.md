# KB-6110: HX-5000 8.0 multicast replication can starve uplink buffers during short bursts

## Summary
On Helix HX-5000 running 8.0, heavy VXLAN multicast replication can temporarily exhaust shared egress buffering on a leaf switch. The condition presents as brief loss on unrelated unicast traffic even when the uplink is not continuously saturated.

## Symptoms
Operators typically report intermittent packet loss or microbursts on traffic that does not use multicast, most often on a fabric leaf carrying VXLAN EVPN workloads. The event recurs every few minutes under load and is usually short-lived, making it difficult to correlate with interface utilization alone.

During an event, `show queue counters` shows discard increments on the uplink queue, commonly in bursts of 200 to 600 packets. Interface utilization often remains below 80 percent, which distinguishes this condition from simple oversubscription. A corresponding `%BUF-3-OVERFLOW` log may appear at the time of the drop.

## Diagnosis
1. Run `show queue counters` on the affected uplink and look for sudden discard increments on the egress queue that align with the loss event. Bursts of 200 to 600 discards with otherwise stable counters are consistent with this issue.
2. Run `show interfaces ethernet <port> counters` and confirm that total utilization stays below 80 percent while the drops occur. Sustained near-line-rate utilization points to a different congestion problem.
3. Run `show vxlan multicast statistics` and check for high replication activity on the same leaf. A high fanout rate shortly before the discard burst supports the diagnosis.
4. Check the system log for `%BUF-3-OVERFLOW` entries with timestamps that match the packet loss window. The presence of this message indicates buffer exhaustion in the replication path.
5. If available, run `show hardware buffer summary` and verify that multicast reservations are consuming most of the shared buffer pool. Low remaining headroom during bursty replication is the expected trigger.

## Root cause
In 8.0, the multicast replication engine reserves an excessive amount of shared buffer for fanout and does not release that reservation quickly enough after the burst ends. As a result, the unicast egress queue on the uplink can run out of immediate headroom even when the port is not continuously oversubscribed.

This behavior is specific to the 8.0 release family listed here. It is a resource-management problem in the buffer allocator, not a physical link fault, LACP issue, or spanning-tree event.

## Workaround
1. Reduce multicast fanout on the busiest leaf switches so that replication bursts consume less shared buffer.
2. If possible, move replication-heavy workloads to a separate uplink group to isolate the multicast reservation from latency-sensitive unicast traffic.
3. If the traffic pattern is predictable, shift the burst window outside congestion-sensitive periods to avoid overlapping with critical unicast flows.
4. Apply the buffer tuning parameters in configuration mode and verify that the multicast reservation is lower and the uplink queue has sufficient headroom after the change.

```text
configure terminal
hardware buffer multicast-reservation 12
interface port-channel 20
queue-limit 4096
```

## Resolution
No software fix is available for 8.0, and no upgrade path within the listed release family resolves the issue. To prevent recurrence, keep multicast fanout constrained on the busiest leafs, isolate replication-heavy workloads onto separate uplink groups when possible, and validate queue headroom after any traffic or topology change.
