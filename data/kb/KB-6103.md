# KB-6103: HX-5000 stack master election oscillates in 7.3 when stack cables negotiate at mixed speed

## Summary
On Helix HX-5000 systems running 7.3, a stack with mixed 50 cm and 1 m stack cables can experience repeated master re-elections even though all physical stack links remain up. The condition is most visible when the control plane is moderately busy and the master role changes several times per hour.

## Symptoms
Administrators may observe intermittent stack instability with no corresponding cable failure or link-down event. `show stack` can briefly display members in separate election domains, and the log records repeated re-election activity with %STACK-3-SPLIT-BRAIN events. In affected deployments, the master role may oscillate 2 to 4 times per hour under moderate control-plane load, which can lead to brief management disruption or transient routing protocol resets on the stack master.

The issue is limited to 7.3 and is most likely when stack cable lengths are mixed across the ring. The stack remains electrically intact, but election behavior becomes unstable when one member encounters scheduling delay during keepalive processing.

## Diagnosis
1. Run `show stack` and verify whether the stack is repeatedly re-electing a new master while all members remain present. Affected systems can show members briefly in separate election domains or alternating master/standby state without a port or cable failure.
2. Check `show logging` and look for repeated `%STACK-3-SPLIT-BRAIN` events within a short interval. The log pattern should show election restarts, not physical interface down/up messages.
3. Run `show stack detail` and confirm that all stack links report operational status with no physical loss, CRC storm, or link renegotiation counters increasing. This issue occurs with links up and stable.
4. If supported in the current image, run `show stack election` or the equivalent election-status command and look for frequent changes in the selected master while adjacency scores remain close. An unstable result with consistent link health points to this defect.
5. Check control-plane utilization with `show processes cpu` and confirm whether the system is under moderate load, typically above normal idle but below saturation. Affected systems often show the oscillation when CPU is elevated for control-plane tasks, not when the stack is idle.

## Root cause
In 7.3, the stack election code uses the lowest latency sample from the last three keepalive intervals instead of the current two-way adjacency score. When one member experiences a scheduler delay of about 20 ms, the election result can temporarily favor a different member even though both stack links are still operational.

Mixed 50 cm and 1 m cables can make the observed latency samples less consistent, which increases the chance that the incorrect election input changes from one interval to the next. This causes repeated master re-selection and produces split-brain log entries without any physical stack failure.

## Workaround
1. Standardize the stack cabling so that all members use matched-length stack cables, which reduces latency variance across the ring.
2. Keep control-plane load below 60 percent during the unstable period to minimize scheduling delay spikes that can trigger master oscillation.
3. If a specific master is preferred for operations continuity, set a higher stack member priority on that unit and lower the priority on the other member(s) so election outcomes remain stable.
4. Avoid adding or removing stack members until the system is upgraded, because topology changes can increase the chance of another re-election while the defect is present.

```text
configure terminal
stack member 1 priority 200
stack member 2 priority 100
```

## Resolution
Upgrade the stack to release 7.4 or later. The defect is fixed in 7.4: master election now uses the current adjacency score and ignores transient scheduler delay spikes, which stops the repeated re-election behavior.
