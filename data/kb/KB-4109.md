# KB-4109: Orion OW-20 guest portal sessions fail after standby failover when the portal cookie is pinned to the active node UUID

## Summary
On Orion OW-20 running 4.9, guest portal sessions can fail immediately after a redundancy switchover when the portal cookie was issued by the former active node. The client is redirected back to the login page and never transitions to an authorized state, even though the guest database and credentials remain valid.

## Symptoms
Guest users can log in successfully while the original active controller is serving portal traffic. After a standby failover, the browser enters a redirect loop to the guest portal login page within 1-2 seconds, and the session remains in a pending or unauthenticated state instead of reaching `authorized`.

On the portal status view, repeated cookie validation failures appear for the same client session. Existing guest sessions are lost after the switchover, but other controller services remain normal and the guest database contents are still present.

## Diagnosis
1. 1. Run `show redundancy status` and confirm that a failover or role change occurred shortly before the guest session failure. Look for the active node UUID changing between the pre-failover and post-failover state.
2. 2. Run `show client detail <mac>` for an affected guest client. Verify that the client remains in portal authentication state and does not advance to `authorized` after the redirect loop starts.
3. 3. Check portal logs for `%PORTAL-5-COOKIE_MISMATCH`. This indicates the controller rejected the session cookie after the node change.
4. 4. If available, enable portal debugging during a test switchover and repeat the login flow. Affected systems log cookie signature validation failures immediately after the standby becomes active.
5. 5. Confirm that the issue is specific to 4.9 by checking the running release with `show version`; the condition should not reproduce on 5.0 or later.
6. 6. Verify that the guest database is intact by checking that existing guest records remain present, even though active sessions are invalidated after the failover.

## Root cause
In release 4.9, the guest portal cookie is signed with the active node UUID as part of the session token. During a redundancy failover, the standby node presents a different UUID, so the signature no longer matches the cookie previously issued by the former active node. The portal therefore rejects the session even though the guest identity and database entry are still valid.

This behavior affects guest portal state only. Other controller functions may continue operating normally, which can make the problem appear intermittent unless a failover occurs during an active guest registration or reauthentication window.

## Workaround
1. 1. Before any planned switchover, check redundancy state and schedule the change only when guest portal usage is low.
2. 2. Reduce the guest session lifetime temporarily so users are prompted to reauthenticate quickly after maintenance, then plan to clear or refresh browser cookies after the switchover.
3. 3. For maintenance windows where guest access must remain available, keep guest portal traffic on the current active node by inhibiting failover until registration is complete.
4. 4. If a failover already occurred, clear the affected browser cookie and have the guest user authenticate again on the new active node before restoring normal redundancy operation.

```text
show redundancy status
guest-portal session timeout 15
redundancy failover inhibit
```

## Resolution
The defect is fixed in release 5.0. In that release and later, guest portal cookies are validated against the redundancy cluster identity instead of the active node UUID, so sessions survive a standby failover without cookie mismatch errors.
