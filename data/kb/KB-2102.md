# KB-2102: Aurora AR-900 9.1.4 BFD sessions stop transmitting after 64-bit counter wrap on long-lived peers

## Summary
On Aurora AR-900 running 9.1.4, long-lived BFD sessions can stop transmitting control packets after the system uptime reaches the 64-bit monotonic counter wrap point. The receive side may still process late replies, so the session can appear Up locally until the remote peer declares the session down.

## Symptoms
After roughly 49.7 days of continuous operation with 50 ms transmit intervals, one or more BFD sessions stop sending control packets while the remote side continues to reply to the last valid state. `show bfd neighbors detail` shows the local discriminator as Up, but the transmit counter is frozen and the peer times out after 300 ms to 900 ms depending on the negotiated multiplier. The problem typically affects a small set of long-lived sessions first and then repeats on others after the system uptime crosses the wrap point.

Operators may also see a burst of BFD session flaps on adjacent peers as the affected sessions fail in sequence. The issue is most visible on deployments with aggressive BFD timers, especially where the same control-plane process has been up continuously since before the wrap threshold.

## Diagnosis
1. Run `show bfd neighbors detail` and verify that one or more affected neighbors remain in Up state locally while the transmit counter does not increase over successive samples.
2. Run `show bfd neighbors` and check whether the peer state transitions to Down or Init after 300 ms to 900 ms, matching the configured detection multiplier.
3. Check system uptime with `show system uptime`; if the platform uptime is near or above 49 days on 9.1.4, the timing aligns with the counter-wrap trigger.
4. Use `show log` and look for `%BFD-3-ERR-BFD-2201` entries on the time of failure; the log commonly appears when the transmit wheel stops advancing.
5. If available, run `debug bfd events` and confirm that receive processing continues while transmit scheduling for the affected session no longer advances.

Example output:

## Root cause
In 9.1.4, the BFD scheduler used a signed comparison when calculating the next transmit deadline from a 64-bit monotonic counter. Once the counter crossed the sign bit boundary, the transmit wheel stopped advancing for affected sessions even though the receive path remained active.

Because the receive path continued to accept valid peer packets, the local session could remain reported as Up for a short period even though no new control packets were transmitted. This created an asymmetric failure mode that is most apparent on peers with short transmit and detection intervals.

## Workaround
1. Plan a maintenance window and restart the BFD process, or reload the device before the platform uptime reaches 49 days so the scheduler state is reset.
2. For noncritical peers, temporarily relax BFD sensitivity by increasing the transmit interval and detection multiplier to reduce the likelihood of immediate peer timeout; apply the provided BFD timer configuration in the BFD hierarchy.
3. Verify that session counters resume incrementing with `show bfd neighbors detail` and that peer state remains stable after the change.
4. If the platform is already past the wrap point and sessions continue to stall, perform a controlled process restart or reload rather than waiting for spontaneous recovery.

```text
configure
router bfd
timers 200 200 5
```

## Resolution
The defect is fixed in release 9.1.6. In that release, BFD transmit scheduling correctly handles 64-bit counter wrap and no longer stalls after extended uptime.
