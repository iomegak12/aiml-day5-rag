# KB-4108: Orion OW-20 4.9 may omit Vendor-Specific attribute 26 from Access-Challenge processing when the reply contains 13 attributes

## Summary
On Orion OW-20 controllers running 4.9, 802.1X authentication can fail intermittently when the external RADIUS server returns an Access-Challenge with a large attribute set. The controller may process the first challenge successfully, then lose tunneled policy attributes on the next challenge, leaving the client stuck in authentication until timeout. The defect is corrected in 5.0.

## Symptoms
This issue is seen during 802.1X authentications against external RADIUS servers, most often with tunneled EAP methods that depend on Vendor-Specific attribute 26. The session typically reaches the first challenge, then stalls after the second Access-Challenge because the controller no longer forwards the policy attributes required by the tunneled exchange.

Affected clients remain in `authenticating` for approximately 15 to 20 seconds before the session fails. The problem is most reproducible when the Access-Challenge contains 13 or more attributes. In that case, authentication may succeed for some users and fail for others depending on the exact attribute ordering returned by the server.

## Diagnosis
1. Run `show client detail <mac>` during a failing authentication and verify that the client remains in `authenticating` after the second Access-Challenge. If the session does not progress to an authorized state and eventually times out, continue with the next steps.
2. Check controller logs for `%RADIUS-4-ATTR_DROP`. This indicates the controller dropped an attribute during Access-Challenge repacking.
3. Review the recent RADIUS exchange with `show logging last 50` and confirm that the challenge reply contains 13 or more attributes before the failure occurs.
4. If packet capture is available on the controller uplink, confirm that Vendor-Specific attribute 26 is present in the server reply but missing from the repacked challenge forwarded internally by the controller.
5. Compare a working and failing authentication. If the failure occurs only when the Access-Challenge attribute count exceeds 12, this matches the known defect in 4.9.
6. If the controller is running 4.9 and the above conditions are met, treat the issue as the attribute truncation defect described here.

Example output:

```text
2026-03-14T02:13:07Z %RADIUS-4-ATTR_DROP: dropped attribute during challenge repack, session 7f4c2a91 client 198.51.100.24
2026-03-14T02:13:07Z %RADIUS-6-AUTH_STATE: client 198.51.100.24 state authenticating
2026-03-14T02:13:10Z %RADIUS-6-AUTH_STATE: client 198.51.100.24 state authenticating
2026-03-14T02:13:22Z %RADIUS-4-TIMEOUT: authentication timed out for client 198.51.100.24

client mac: 00:11:22:33:44:55
state: authenticating
method: 802.1x tunneled-eap
last-radius-code: access-challenge
radius attributes received: 13
vendor-specific attr 26: present in server reply, not present in repacked challenge
```

## Root cause
In release 4.9, the RADIUS encoder used during Access-Challenge repacking for internal policy handling truncates the attribute list after 12 entries. When the external server returns 13 or more attributes, Vendor-Specific attribute 26 is commonly positioned beyond the truncation point and is removed without a corresponding log entry from the encoder path.

Because tunneled EAP methods depend on that vendor-specific policy data to continue the exchange, the client cannot complete the next step of authentication. The session remains in the authenticating state until the RADIUS timer expires.

## Workaround
1. Reduce the number of attributes returned in the Access-Challenge to 12 or fewer, or modify the server policy so that nonessential attributes are omitted from the challenge reply.
2. If the policy server supports attribute ordering, place Vendor-Specific attribute 26 earlier in the reply so it is not affected by the 12-entry truncation limit.
3. If multiple policy servers are available, direct the request to a server profile that returns tunneled policy attributes first.
4. Verify the workaround by repeating a failed authentication and confirming that the client completes 802.1X without remaining in `authenticating`.

```text
show client detail <mac>
radius-server attribute-order vendor-first
show logging last 50
```

## Resolution
The defect is fixed in release 5.0. In 5.0 and later, Access-Challenge repacking retains all attributes and no longer truncates the list at 12 entries, so Vendor-Specific attribute 26 is preserved for tunneled EAP processing.
