# KB-4106: Orion OW-20 5.0 may miss FT key pushes during heavy 802.11r roaming

## Summary
Orion OW-20 release 5.0 can miss fast transition (802.11r) key pushes during heavy roaming activity. In affected deployments, clients complete reassociation but still experience short service gaps because the controller falls back to a slower transition path.

## Symptoms
Voice and handheld clients may roam successfully yet experience 150-300 ms interruptions every few roam events. On the controller, the reassociation completes, followed by an FT key timeout, and client detail output shows `ft fallback: yes` for clients expected to remain on the fast transition path.

The issue is most often seen when roaming density exceeds about 40 clients within a 10-second interval. It is reproducible on SSIDs with 802.11r enabled and is more visible on latency-sensitive traffic such as voice.

## Diagnosis
1. 1. Verify that the affected SSID has 802.11r enabled with `wlan corp ft enable`. If FT is disabled, this issue does not apply.
2. 2. Run `show client detail <mac>` for a client that experienced the gap. Confirm that reassociation succeeded, but `ft fallback: yes` is present and the roam history shows a transition away from the FT path.
3. 3. Check controller event logs for `%ROAM-5-FT_KEYTIMEOUT` within the same roam window. The timeout typically appears after reassociation completes.
4. 4. Review roam density during the failure window. Correlate client movement events and confirm that more than 40 clients roamed within 10 seconds.
5. 5. If available, inspect roam processing counters or debug output for delayed FT key push completion. The affected pattern is a batched push that completes after the 300 ms window.
6. 6. Compare behavior after reducing the roam burst rate. If the issue disappears when fewer than 30 clients roam in 10 seconds, the defect is consistent with this condition.

Example output:

```text
2026-03-14T02:13:07Z %ROAM-6-REASSOC: client 198.51.100.24 reassociated to ap-17
2026-03-14T02:13:07Z %ROAM-5-FT_KEYTIMEOUT: ft key push did not complete before 300 ms window for client 198.51.100.24
2026-03-14T02:13:08Z %ROAM-6-CLIENTPATH: client 198.51.100.24 switched to slow transition sequence

client detail 198.51.100.24
  ssid: corp
  ft enabled: yes
  reassociation: success
  transition path: ft
  ft fallback: yes
  roam latency: 184 ms
  last ap: ap-12
  current ap: ap-17
```

## Root cause
In release 5.0, the roaming daemon batches FT key pushes to reduce CPU usage. Under high roam density, the batch flush can be delayed by the per-client state cleanup thread.

When more than about 40 clients roam within 10 seconds, the FT key push can miss the 300 ms completion window. The client then reverts to a slower transition sequence even though reassociation succeeded, which increases roam latency and can interrupt real-time traffic.

## Workaround
1. 1. Confirm that the SSID is using 802.11r and that the affected clients show FT fallback in `show client detail <mac>`.
2. 2. Reduce roam burst density during testing or operations so that fewer than 30 clients roam in any 10-second interval.
3. 3. If the roaming profile permits it, reduce the client cleanup batch size so the FT flush completes within 150 ms.
4. 4. Re-run the roaming test and verify that reassociation completes without `%ROAM-5-FT_KEYTIMEOUT` and that `ft fallback: yes` no longer appears for the affected clients.

```text
show client detail <mac>
wlan corp ft enable
roam batch-size 8
```

## Resolution
The defect is fixed in release 5.1. In 5.1, FT key pushes are sent immediately when the client enters reassociation, regardless of cleanup batching.
