# KB-3103: Nimbus NF-300 5.0.9: standby drops replicated sessions after split-brain recovery

## Summary
In Nimbus NF-300 5.0.9, a brief split-brain event can leave the standby unit with an incomplete replicated session table even though high-availability state shows synchronized. The issue is caused by a stale replay sequence during recovery and can persist for several minutes until a full synchronization completes.

## Symptoms
After a split-brain recovery, the standby unit returns to service but does not immediately contain the same session population as the active unit. `show ha status` reports the peers as synced, however `show session table summary` on the standby remains 20,000 to 40,000 entries lower than the active unit for several minutes. Operators may also see transient HA replay messages indicating that session replication is not advancing normally.

This condition is usually visible only after a brief loss of the failover relationship and may not reproduce during routine failover testing. Traffic continues to pass, but stateful flows that depend on the missing entries can be dropped or re-established unnecessarily until the table converges.

## Diagnosis
1. Run `show ha status` on both units and confirm that the cluster has recovered from split-brain and reports synchronized or healthy peer state.
2. Run `show session table summary` on the active and standby units. If the standby count is lower by tens of thousands of entries for more than a few minutes after recovery, suspect stale replication.
3. Check system logs for `%HA-4-RSYNC_STALE_SEQ` immediately after the peer returns. The presence of this message indicates the standby accepted the peer sequence number before its local replay queue was drained.
4. If available in your maintenance window, enable HA replay debug and review whether older updates are being discarded as stale during recovery. The key indicator is replay progress stopping while the HA state remains synced.
5. Repeat the session-table check after 5 to 10 minutes. If counts converge only after the next full sync cycle, the issue matches this defect rather than a persistent link failure.

Example output:

```text
2026-03-14T02:13:07Z %HA-4-RSYNC_STALE_SEQ: standby accepted peer sequence 184233 before local replay queue drained; discarding 327 stale updates
2026-03-14T02:13:08Z %HA-6-STATE_CHANGE: ha peer 198.51.100.2 state changed to synced

nimbus# show ha status
cluster state           : synchronized
local role              : standby
peer role               : active
replication status      : synced
last failover event     : 2026-03-14T02:12:54Z

nimbus# show session table summary
active sessions         : 218764
standby replicated      : 196902
missing replicated      : 21862
```

## Root cause
During split-brain recovery, the replication agent advances the standby sequence number as soon as the peer is reachable, before the local replay queue has fully drained. If the queue still contains older updates, those records are judged stale and dropped instead of being applied to the session table.

As a result, the standby can report a healthy HA state while its replicated session table remains incomplete. Convergence occurs only after the next full synchronization cycle repopulates the missing state.

## Workaround
1. Verify the cluster has recovered and that the peer is reachable before making any changes. Confirm that the issue is the post-recovery session-count gap rather than an ongoing failover fault.
2. During the maintenance window, trigger a full HA resynchronization rather than waiting for incremental replay to complete. This forces the standby to rebuild its replicated state from the active unit.
3. After initiating the resync, keep the failover links stable for at least 120 seconds so the replay queue can drain without another role change.
4. Recheck HA and session-table status after the resync completes and confirm that the standby count returns to parity with the active unit.

```text
show ha status
config
ha resync full
commit
```

## Resolution
The defect is fixed in release 5.2.2. In that release, the standby defers sequence-number advancement until the replay queue is empty, preventing stale updates from being discarded during split-brain recovery.
