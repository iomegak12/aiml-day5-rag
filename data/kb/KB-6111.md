# KB-6111: Upgrade from 7.2 to 7.4 can fail when saved transceiver calibration data exceeds 32 KB

## Summary
An in-service upgrade from Helix HX-5000 7.2 to 7.4 can fail during the image migration phase when saved transceiver calibration data exceeds the parser limit. The failure is most common on chassis with many populated optics or long DOM history retention, and the upgrade rolls back after a management-plane restart.

## Symptoms
During an in-service upgrade from 7.2 to 7.4, the process typically progresses to 78 to 82 percent and then pauses briefly before the management plane restarts once and the device rolls back to the previous release. Upgrade logs include a calibration import failure with ERR-UPG-2207, and the rollback may be followed by noticeably slow execution of `show interfaces transceiver detail` on systems with many optics installed.

Operators may also notice that the affected chassis has extensive saved DOM history for transceivers, especially on platforms that have had frequent optic replacements or long retention periods. The upgrade failure is reproducible on the same hardware and software state until the calibration history is reduced.

## Diagnosis
1. Run `show version` and confirm the active release is 7.2 and the attempted target is 7.4; this issue is specific to upgrades from 7.2 to 7.4.
2. Run `show logging | include ERR-UPG-2207` and look for a calibration import failure at 78 to 82 percent of the upgrade workflow.
3. Run `show interfaces transceiver detail` and note whether the command returns slowly, especially on chassis with many populated ports; a 20 to 30 second delay after rollback is consistent with large saved calibration records.
4. Run `show file systems` or the local upgrade status command used by your operations workflow and confirm the upgrade aborted after the management-plane restart and reverted to the prior image.
5. If available, run `show interfaces transceiver detail | include calibration` and verify that multiple optics report retained calibration history rather than a compact current-state record.

## Root cause
The 7.4 image expects a compact transceiver calibration record, but some 7.2 systems store expanded DOM history blocks that can exceed 32 KB per chassis. During upgrade, the migration parser does not trim these legacy records before conversion, so the boot loader rejects the converted configuration and aborts the commit.

This condition is data-dependent rather than hardware-specific. Chassis with more optics, longer retention of DOM history, or repeated optic swaps are more likely to accumulate oversized calibration data and trigger the failure path.

## Workaround
1. Schedule the upgrade in a maintenance window and back up the running configuration before making changes.
2. Reduce the amount of retained transceiver calibration data by disabling nonessential DOM history, then save the configuration and reload the chassis so the smaller record set is rebuilt.
3. If the chassis has many populated optics, remove and reseat the most recently installed modules before retrying the upgrade so the calibration cache is regenerated in a smaller form.
4. Retry the in-service upgrade from 7.2 to 7.4 after the system is back in service and verify that the upgrade proceeds past the 80 percent migration point without a management-plane restart.

```text
configure terminal
no transceiver calibration-history
write memory
reload
```

## Resolution
This defect is fixed in release 7.5. The migration process now truncates legacy transceiver history before the target image is committed, preventing calibration records from exceeding the parser limit during upgrade.
