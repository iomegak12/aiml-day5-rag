# KB-5110: Atlas SD-WAN 3.2: migration drops per-interface LTE tunnel MTU when the profile uses a nondefault APN

## Summary
After upgrading Atlas SD-WAN edges from 3.1 to 3.2, LTE transports that use a nondefault APN may lose their configured per-interface tunnel MTU during migration. The tunnel remains established, but traffic larger than the effective post-upgrade encapsulation limit is fragmented or dropped.

This issue affects the edge configuration only after upgrade; branches using the default APN retain the expected MTU value.

## Symptoms
Following a 3.1 to 3.2 upgrade, the LTE interface comes up and the overlay tunnel shows as established, but applications that send larger packets begin to experience fragmentation or loss. In practice, packets above about 1418 bytes fail on the affected circuit, while smaller probes continue to pass.

The post-upgrade running configuration no longer shows the prior `tunnel-mtu` statement on LTE interfaces bound to a custom APN. Branches using the default APN do not show the same configuration loss and continue to operate with the original MTU setting.

## Diagnosis
1. Run `show sdwan tunnels` on the edge and verify that the LTE tunnel is in `established` state. If the tunnel is up but user traffic fails at larger packet sizes, continue with MTU verification.
2. Run `show running-config interface lte0` and inspect the LTE interface stanza. If the pre-upgrade `tunnel-mtu` line is missing after the upgrade, this matches the defect.
3. Run `show app-route sla-class` or the relevant path-policy view to confirm that routing decisions are unchanged and that the symptom is limited to packet size handling rather than path selection.
4. Send 1400-byte and 1472-byte probes across the LTE path. If 1400-byte traffic passes and 1472-byte traffic fragments or fails, the effective tunnel MTU is lower than the configured value.
5. Check the APN binding in the LTE interface configuration. If the interface uses a custom APN and the MTU override disappeared only on that interface, the issue is the 3.2 migration defect.
6. Review edge logs for the upgrade event. A matching `%UPG-5-MTU-MIGRATE` message indicates the migration path processed the LTE interface and omitted the MTU field for a nondefault APN.

## Root cause
The 3.2 migration parser only copies the LTE tunnel MTU when the APN name matches the default profile. If a custom APN is in use, the parser preserves the interface object but silently omits the MTU field, so the overlay inherits the platform default value instead of the configured one.

As a result, the tunnel remains operational, but its effective encapsulation budget is smaller than expected. The defect is limited to migrated LTE interfaces with nondefault APNs and does not affect branches using the default APN.

## Workaround
1. Identify every LTE interface that uses a custom APN on the upgraded edge.
2. Reapply the expected tunnel MTU on each affected LTE interface after the upgrade. Use the value that was configured before migration; in affected deployments this is commonly 1400 bytes.
3. Save the configuration and confirm that the interface stanza now includes the `tunnel-mtu` setting.
4. Validate the path by testing both a 1400-byte probe and a 1472-byte probe. The smaller probe should succeed, and the larger probe should pass only if the end-to-end encapsulation budget allows it.
5. Return the circuit to production only after the larger-packet test behaves as expected for the site design.

```text
interface lte0 tunnel-mtu 1400
commit
```

## Resolution
The defect is fixed in release 3.3. The 3.3 migration preserves LTE tunnel MTU values for both default and nondefault APNs, so upgraded edges retain the configured per-interface MTU setting.
