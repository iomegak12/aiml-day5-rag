# KB-3109: Nimbus NF-300 5.2.0 uneven session-table distribution with asymmetric routing on concentrated /24 traffic

## Summary
On Nimbus NF-300 5.2.0, enabling asymmetric path handling can produce uneven session-table shard utilization when a large volume of flows arrives from a concentrated /24 source or destination prefix. The issue can leave one shard near exhaustion while other shards remain lightly used, resulting in intermittent latency spikes on the flows mapped to the overloaded shard.

## Symptoms
Administrators typically observe that overall session-table usage remains moderate, but one or two shards climb to approximately 88 percent occupancy while the remaining shards stay below 40 percent. The condition usually becomes visible after about 300,000 new sessions are created.

Affected traffic may show brief latency increases of 3 to 4 milliseconds, especially for new sessions assigned to the busiest shard. In some cases, the platform logs %SESSION-4-HASH_SKEW events when shard occupancy crosses the skew threshold, but forwarding continues until the affected shard approaches its capacity limit.

## Diagnosis
1. Run show session table summary and compare shard occupancy values. This issue is indicated when one shard is near 88 percent while other shards remain well below 40 percent.
2. Run show logging last 50 and look for %SESSION-4-HASH_SKEW messages referencing shard imbalance or redistribution delay.
3. Run show session table shard detail to confirm that new sessions from the same /24 prefix are landing on the same worker queue or shard.
4. If asymmetric routing is enabled for the policy set, verify the setting with show running-config session-table and confirm that asymmetric-routing is enabled.
5. Check session growth with show session table summary over time. A sharp rise to approximately 300,000 new sessions followed by a sustained shard imbalance is consistent with this defect.

## Root cause
When asymmetric routing is enabled, the shard allocator in 5.2.0 does not sufficiently mix the low-order bits of the 5-tuple before selecting a worker queue. As a result, many flows from the same /24 prefix are mapped to the same shard instead of being spread across the full shard set.

The load-balancer redistribution threshold is also set too high in this release, so once the imbalance forms it stays localized. The allocator does not trigger redistribution early enough to pull sessions onto other shards, which allows one shard to reach high occupancy while the rest remain underutilized.

## Workaround
1. Determine whether the impacted policy set depends on asymmetric routing handling. If it does not, leave the feature disabled for that policy set.
2. If the traffic source can be re-segmented, split the large /24 into smaller policy groups so session creation is distributed more evenly across shards.
3. Apply the configuration change to disable asymmetric routing handling in the affected policy set, then commit the change.
4. After the change, monitor the busiest shard with show session table summary and keep shard occupancy below 75 percent until an upgraded release can be installed.
5. If occupancy continues to rise above 75 percent, reduce the concentration of new sessions by adjusting policy grouping or traffic steering before re-enabling the feature.

```text
config
session-table asymmetric-routing disable
commit
```

## Resolution
This defect is fixed in release 5.2.2. In that release, session hashing uses the full 5-tuple and shard redistribution is triggered once occupancy exceeds 75 percent, preventing the localized skew seen in 5.2.0.
