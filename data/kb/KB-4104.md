# KB-4104: Orion OW-20 4.8 active-standby sync stalls when the configuration database exceeds 32,768 rows

## Summary
On Orion OW-20 release 4.8, an active-standby redundancy pair can stop applying incremental configuration updates once the configuration database grows beyond approximately 32,768 rows. The standby remains reachable and the redundancy link stays up, but the replicated configuration becomes incomplete and failover may expose stale WLAN and client-policy state.

## Symptoms
In affected 4.8 deployments, administrators typically observe that the standby reports synchronized connectivity to the active controller, but the synchronization state never advances to complete. After the configuration database passes roughly 32,768 rows, the standby stops receiving later incremental updates. A planned or unplanned switchover can therefore cause clients to reauthenticate or briefly lose policy state for 30 to 90 seconds while the new active unit converges.

The event log repeatedly records the sync stall condition at 10-second intervals. `show redundancy status` reports `sync state: partial`, while the configuration database summary continues to increase on the active unit and does not fully match the standby copy.

## Diagnosis
1. Run `show redundancy status` and verify that the redundancy peer is up, but `sync state` remains `partial` rather than `complete`.
2. Run `show configuration database summary` and check whether the total row count is at or above 32,768. Affected systems usually show growth past this threshold before the stall begins.
3. Review the event log for repeated `%REDUNDANCY-4-SYNC_STALL` entries every 10 seconds. The message indicates the incremental sync encoder is no longer advancing.
4. If failover has already occurred, use `show client detail <mac>` for affected clients and confirm that WLAN or client-policy attributes are briefly missing or refreshed after switchover.
5. If redundancy statistics are available on the platform, confirm that the peer link remains established and that only incremental object replication is stalled, not the transport between controllers.

## Root cause
In release 4.8, the incremental synchronization encoder uses a 15-bit row index. Once the configuration database exceeds row 32,767, subsequent rows wrap and are treated as if they were already synchronized. The standby therefore never receives the wrapped objects, even though the redundancy transport remains healthy.

Because the defect is in the incremental encoding logic rather than the peer connection, the active and standby controllers can continue to exchange keepalives and status while the replicated database becomes incomplete. This produces a partial sync state and stale runtime policy after failover.

## Workaround
1. Before any planned failover, review the configuration database size and identify objects that are not required for operations, such as unused AP groups, obsolete WLAN profiles, and stale guest accounts.
2. Reduce the database to below 30,000 rows so there is headroom below the 32,768-row wrap point. Apply the cleanup during a maintenance window to avoid unintended policy changes.
3. After cleanup, confirm that the redundancy status returns to a complete sync state and that the database size remains below the threshold.
4. If immediate failover is required before the database can be reduced, schedule a maintenance window and perform a full configuration resynchronization to repopulate the standby with a complete dataset.

```text
show redundancy status
show configuration database summary
redundancy force-resync
```

## Resolution
This defect is fixed in release 4.9. In that release, incremental synchronization uses a 32-bit object index, which prevents row wrap and allows redundancy sync to complete correctly even when the configuration database exceeds 32,768 rows.
