# KB-6102: HX-5000 7.5 QSFP28 uplinks report intermittent LOS after DOM threshold recalculation

## Summary
On Helix HX-5000 release 7.5, QSFP28 100G uplinks can momentarily drop after a DOM temperature or voltage alarm clears. The port may recover immediately at the optics level, but the switch withdraws the interface for several seconds due to a false loss-of-signal evaluation.

## Symptoms
Operators typically see a brief down/up cycle on a 100G Ethernet uplink after a transceiver DOM alarm clears. `show interfaces transceiver detail` indicates that optical power, temperature, and voltage have returned to normal, yet the port remains out of service for 3 to 5 seconds before returning to forwarding state.

The remote device usually records a clean LOS transition with no corresponding physical fiber event. This behavior is intermittent and is most commonly reported on QSFP28 modules operating within vendor specifications on 7.5 systems.

## Diagnosis
1. Run `show interfaces transceiver detail` on the affected port and confirm that DOM values return to normal immediately after the alarm clears. Look for temperature or voltage readings inside the expected operating range while the interface is still withdrawn.
2. Run `show interface ethernet 1/49` and verify that the port state changes to down and then back up without a persistent local fault. The issue is consistent with a short administrative/operational withdrawal rather than a sustained optics failure.
3. Check the system log with `show logging | include TRANSCEIVER` and confirm a `%TRANSCEIVER-4-LOS` entry at the time of the event. The log should show a loss-of-signal assertion immediately after a DOM threshold clear.
4. If available, compare the remote switch logs for the same time window. A clean LOS transition on the peer, with no CRC burst or physical-layer degradation, supports this defect rather than cabling damage.
5. Use `show interface ethernet 1/49 counters` after recovery. Absence of persistent input errors, symbol errors, or flaps outside the brief interval helps distinguish this issue from a bad optic or dirty fiber.

## Root cause
In release 7.5, the transceiver manager recalculates alarm thresholds after each DOM read. When a temperature or voltage alarm clears, the code briefly reevaluates link state against the newly calculated limits before the debounce timer completes. On affected QSFP28 optics, that transient reevaluation can assert loss of signal even though the module is operating within specification.

The result is a spurious `%TRANSCEIVER-4-LOS` event followed by a short port withdrawal. The condition is not caused by sustained optical degradation and does not indicate a fiber fault if the module readings remain normal.

## Workaround
1. On the affected interface, disable aggressive DOM alarm action so that a transient threshold recalculation does not force link-down behavior.
2. Keep the uplink in service if the DOM readings remain within the normal operating range and the port stabilizes after the brief event.
3. If the link is business-critical and repeated flaps are operationally disruptive, schedule migration of the uplink to a system running a fixed release.

```text
configure terminal
interface ethernet 1/49
transceiver alarm-action link-down disable
```

## Resolution
This defect is fixed in release 7.6. In that release, threshold recomputation no longer triggers link-state reevaluation until the 5-second debounce timer completes, preventing the spurious LOS assertion on QSFP28 uplinks.
