# KB-2103: Aurora AR-900 9.2.0 OSPF adjacency repeatedly resets on multiaccess networks with MTU mismatch

## Summary
On Aurora AR-900 9.2.0, OSPF adjacencies on broadcast or other multiaccess networks can fail to converge when the local interface MTU is larger than the peer MTU. The neighbor oscillates between ExStart and Down, preventing the adjacency from reaching Full and causing repeated LSDB churn.

## Symptoms
This issue is typically seen on broadcast segments where the AR-900 9.2.0 interface is configured with an MTU of 1500 bytes and the neighboring router advertises 1492 bytes or lower. The OSPF neighbor table repeatedly transitions from ExStart to Down at roughly 20 to 30 second intervals, and the adjacency never stabilizes in Full state.

During the flap, operators may observe increased LSDB activity, often in the range of 100 to 300 LSAs per minute, along with recurring adjacency reset logs. The problem is most visible after the first DBD exchange succeeds, then subsequent database description packets are rejected as inconsistent.

## Diagnosis
1. Run `show ospf neighbor` and confirm the affected neighbor remains in ExStart or cycles back to Down instead of reaching Full.
2. Run `show ospf interface ethernet 1/1` and compare the local interface MTU with the neighbor MTU reported in the output; the issue is consistent with a local MTU of 1500 and a remote MTU of 1492 or lower.
3. Run `show ospf database` and check for elevated LSA refresh or churn rates during the adjacency flap; sustained increases of 100 to 300 LSAs per minute support this diagnosis.
4. If packet captures are available, inspect OSPF DBD packets on the segment and confirm that the neighbor accepts the first exchange, then resets after subsequent DBD packets when the MTU values differ.
5. Run `debug ospf adj` during a maintenance window and look for repeated ExStart negotiation, MTU mismatch handling, and adjacency reset messages associated with `%OSPF-4-ADJ-EXSTART`.

Example output:

```text
2026-03-14T02:13:07Z %OSPF-4-ADJ-EXSTART: neighbor 198.51.100.2 on ethernet 1/1 moved to ExStart due to database description exchange inconsistency
2026-03-14T02:13:07Z ospf[2147]: neighbor 198.51.100.2 state change ExStart -> Down reason=adjacency reset
2026-03-14T02:13:29Z ospf[2147]: neighbor 198.51.100.2 state change Down -> ExStart
2026-03-14T02:13:41Z ospf[2147]: dbd rx on ethernet 1/1 local-mtu=1500 remote-mtu=1492 accepted-first=true accepted-subsequent=false
2026-03-14T02:13:41Z ospf[2147]: lsdb churn rate=184 lsas/min during adjacency flap
```

## Root cause
In release 9.2.0, the OSPF database description exchange incorrectly reuses the cached local MTU value after the first negotiation attempt. When the neighbor advertises a smaller MTU, the router accepts the initial DBD packet but later treats subsequent packets as inconsistent with the cached value.

This causes the adjacency machine to restart the negotiation and move the neighbor back to ExStart. On multiaccess networks, the repeated reset is visible as a periodic ExStart/Down loop and continuous LSDB churn.

## Workaround
1. Confirm that both peers can safely use the same MTU, then set a matching MTU on the involved interfaces during a maintenance window.
2. If the topology supports it, convert the adjacency to point-to-point operation to avoid the multiaccess DBD behavior that triggers the defect.
3. If MTU alignment is not possible, apply `ip ospf mtu-ignore` on both peers during the same maintenance window so OSPF does not reject the DBD exchange based on the MTU mismatch.
4. After applying the workaround, verify that the neighbor transitions to Full with `show ospf neighbor` and that adjacency resets stop recurring.

```text
configure
interface ethernet 1/1
ip ospf mtu-ignore
```

## Resolution
This defect is fixed in release 9.2.1. In that release, OSPF re-evaluates the remote MTU on every DBD exchange, preventing the repeated ExStart resets on multiaccess networks with MTU mismatch.
