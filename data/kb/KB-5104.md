# KB-5104: Atlas SD-WAN 3.1: upgrade rewrites LTE tunnel MTU to 1500 on dual-SIM edges

## Summary
After upgrading an Atlas SD-WAN edge from 3.0 to 3.1, dual-SIM LTE sites may continue to form overlay tunnels but begin dropping larger packets. The tunnel state remains up in `show sdwan tunnels`, while application traffic above the effective path MTU fails and the edge logs repeated MTU mismatch notices.

## Symptoms
This issue is observed only on edges that had an explicit LTE tunnel MTU configured before the upgrade and that present two modem profiles on the same LTE interface. Following the upgrade to 3.1, the overlay may remain established, but flows with payloads above roughly 1420 bytes experience loss, retransmissions, or intermittent fragmentation alerts. Operators commonly report that small probes succeed while larger pings or application sessions fail across the LTE transport.

On affected edges, `show sdwan tunnels` reports the tunnel as up and forwarding, which can delay detection. The edge log contains repeated upgrade and MTU mismatch messages, and the configured tunnel MTU shown in the running configuration no longer matches the pre-upgrade value.

## Diagnosis
1. Run `show sdwan tunnels` on the affected edge and confirm the LTE tunnel is up while packet loss or fragmentation is reported only for larger traffic sizes.
2. Run `show running-config interface lte0` and check whether `tunnel-mtu` is absent or has reverted to the default 1500 bytes after the upgrade.
3. Run `show app-route sla-class` if application-aware routing is in use and verify whether the SLA class is marking the LTE path degraded due to loss or reordering on larger probes.
4. Generate a size-limited test from the edge or a reachable host using 1472-byte ICMP payloads. If smaller pings succeed but 1472-byte probes fail, the path MTU is inconsistent with the expected LTE tunnel MTU.
5. Check the edge log for upgrade migration notices and MTU mismatch entries. The presence of `%UPG-5-MTU-MIGRATE` together with repeated MTU warnings indicates the migration did not preserve the configured LTE tunnel MTU.

Example output:

```text
2026-03-14T02:13:07Z edge01 %UPG-5-MTU-MIGRATE: interface lte0 dual-sim profile detected, applying default tunnel mtu
2026-03-14T02:13:09Z edge01 %TUN-4-MTU-MISMATCH: lte0 configured mtu 1500 exceeds carrier path mtu 1420
2026-03-14T02:13:11Z edge01 %TUN-4-FRAG-ALERT: overlay packet size 1472 dropped on tunnel lte0

edge01# show sdwan tunnels
name     state  transport  local-ip       remote-ip      mtu  loss  latency
lte0     up     lte        198.51.100.14  203.0.113.21   1500  0.0%  48ms

edge01# show running-config interface lte0
interface lte0
  sim-profile primary
  sim-profile secondary
  tunnel-mtu 1500
```

## Root cause
The 3.1 migration script copies the LTE profile but falls back to the default tunnel MTU when it detects two modem profiles on the same interface. As a result, the saved pre-upgrade MTU value is not preserved in the upgraded running configuration.

Because the edge advertises an encapsulation size larger than the carrier LTE link can carry, large overlay packets exceed the effective path MTU. The tunnel stays operational, but traffic that depends on the original smaller MTU is fragmented or dropped.

## Workaround
1. After the upgrade, identify each affected LTE interface on the edge and compare the running configuration with the pre-upgrade tunnel MTU value.
2. Reapply the correct tunnel MTU on the LTE interface. For most carrier LTE links, use a value between 1400 and 1420 bytes; 1400 bytes is a safe starting point when the original value is unknown.
3. Commit the configuration and wait for the overlay to reconverge.
4. Retest with 1472-byte pings to the remote endpoint or next-hop service. Confirm that larger payloads now pass without fragmentation or loss before returning the site to service.

```text
interface lte0 tunnel-mtu 1400
commit
```

## Resolution
The defect is fixed in release 3.2. In that release, the migration preserves the configured LTE tunnel MTU across dual-SIM upgrades, preventing the tunnel from advertising an MTU larger than the LTE path can support.
