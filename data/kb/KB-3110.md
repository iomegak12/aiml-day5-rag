# KB-3110: Nimbus NF-300 5.2.0 session-table imbalance after enabling asymmetric routing on large-prefix traffic

## Summary
On Nimbus NF-300 release 5.2.0, enabling asymmetric path handling can cause session-table occupancy to skew heavily toward one or two shards when traffic contains large, repeated prefixes. This can produce intermittent latency spikes on flows that hash into the overloaded shard. The issue is corrected in 5.2.2.

## Symptoms
After asymmetric routing is enabled on 5.2.0, the session table may stop distributing new entries evenly across shards. Operators typically observe one or two shards reaching about 88 percent occupancy while the remaining shards remain below 40 percent, even though total session count is still below the platform-wide limit. The imbalance usually becomes visible after approximately 300,000 new sessions and may coincide with intermittent latency spikes of 3 to 4 milliseconds on affected flows.

The condition is most common when traffic sources share a large common prefix, such as many hosts within the same /24, because new sessions are directed to the same worker queue instead of being spread across available shards.

## Diagnosis
1. Run `show session table summary` and check per-shard occupancy. This issue is indicated when one or two shards are near 88 percent while other shards remain below 40 percent.
2. Run `show session table detail` and confirm that the hottest shard continues to accept new entries while the others remain largely static. A persistent skew across multiple polling intervals supports this defect.
3. Run `show session table statistics` and look for a sharp increase in session inserts without a corresponding increase across all shards. The imbalance usually appears after roughly 300,000 new sessions.
4. If asymmetric routing is enabled for the affected policy set, verify the policy scope and traffic mix. A concentration of sessions from the same /24 or similar prefix is a strong indicator that the shard allocator is not dispersing flows correctly.
5. Check system logs for the hash-skew event. A matching `%SESSION-4-HASH_SKEW` message confirms that the platform detected uneven shard distribution.

Example output:

```text
2026-03-14T02:13:07Z %SESSION-4-HASH_SKEW shard-2 occupancy 88% exceeds distribution threshold; asymmetric routing active on policy-set edge-apps
2026-03-14T02:13:07Z session-table summary
shard 0: entries 112430 occupancy 37%
shard 1: entries 108992 occupancy 36%
shard 2: entries 266104 occupancy 88%
shard 3: entries 117208 occupancy 39%
total: 604734 entries
asymmetric-routing: enabled
hot-shard: 2
```

## Root cause
The shard allocator in 5.2.0 does not mix the low-order bits of the 5-tuple when asymmetric routing is enabled. As a result, sessions originating from the same /24 are likely to hash into the same worker queue, creating a persistent imbalance in one shard.

In addition, the redistribution threshold is set too high, so the load balancer does not move enough new sessions to other shards once the skew begins. The imbalance therefore persists instead of being corrected automatically.

## Workaround
1. Identify the affected policy set and confirm that asymmetric routing handling is enabled for that traffic.
2. Disable asymmetric routing handling for the affected policy set using the session-table configuration mode, then commit the change. This prevents new sessions from being pinned to the same shard.
3. If asymmetric routing must remain enabled, split the large prefix into smaller policy groups so session distribution is less concentrated.
4. Monitor `show session table summary` until the hottest shard remains below 75 percent occupancy. If occupancy continues to rise, keep the workaround in place until a fixed release is installed.

```text
config
session-table asymmetric-routing disable
commit
```

## Resolution
The defect is fixed in release 5.2.2. In that release, session hashing incorporates the full 5-tuple and shard redistribution is triggered once occupancy exceeds 75 percent, preventing the imbalance observed in 5.2.0.
