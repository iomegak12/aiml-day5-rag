# KB-5107: Atlas SD-WAN 3.3: reporting jobs consume excessive CPU when flow history exceeds 7 days

## Summary
On Atlas SD-WAN 3.3 orchestrators, scheduled reports can consume excessive CPU when flow-history retention exceeds roughly 7 days. The issue is most visible on systems with large datasets, where reporting jobs run much longer than expected and can delay other orchestrator activity.

This article describes the symptoms, how to confirm the condition, and the recommended mitigation.

## Symptoms
On 3.3 orchestrators with long retention, scheduled reports begin taking 20 to 30 minutes instead of the expected 3 to 4 minutes once flow history grows past roughly 7 days. During the job window, CPU on the reporting service can remain above 85 percent, and dashboard refreshes lag by several minutes.

The system typically remains operational, but concurrent policy pushes or other orchestrator tasks may be delayed while the report job is running. Operators may also observe the reporting process generating repeated high-CPU alerts or extended job completion times without a corresponding increase in report size.

## Diagnosis
1. Check the active reporting retention setting with `show reporting config`. A retention value above 7d on 3.3 is consistent with this issue; 3d to 5d is typically not affected.
2. Review current report execution state with `show reporting jobs`. Look for scheduled jobs with runtime increasing into the 20-30 minute range or jobs that remain in running state longer than expected.
3. Inspect service CPU with `show processes cpu sorted`. A sustained `reporting` process CPU above 85 percent during the report window supports this condition.
4. Check system logs with `show log | include ERR-ORCH-5178`. The presence of this message during report execution confirms the known reporting scaling limit.
5. If policy updates are delayed, verify orchestrator contention with `show orchestrator tasks`. A backlog that aligns with the report window indicates the report job is competing for CPU resources.
6. Correlate the report start time and dataset size using `show reporting history`. A large flow-history set, commonly above 5 million rows, matches the expected trigger condition.

Example output:

```text
2026-03-14T02:13:07Z reporting[2418]: starting scheduled flow report tenant=all window=24h
2026-03-14T02:13:11Z reporting[2418]: scan complete rows=5823417 retained=8d
2026-03-14T02:13:12Z reporting[2418]: %REPORTING-4-INFO: building in-memory sort for flow-history set
2026-03-14T02:22:40Z orchestrator[1183]: ERR-ORCH-5178 reporting job exceeded expected runtime cpu=88%
2026-03-14T02:38:19Z reporting[2418]: report completed duration=1507s output=success

atlas-orch-01# show processes cpu sorted
process           cpu   mem
reporting         89%   14%
policy-engine      6%    9%
mgmt-plane        3%    7%
```

## Root cause
In release 3.3, the report generator performs a full in-memory sort of the entire flow-history set before applying tenant and time-range filters. When the retained dataset grows beyond about 5 million rows, the memory footprint and garbage-collection overhead dominate runtime, even when the final report only needs a small subset of records.

This is a scaling limitation in the 3.3 reporting implementation rather than a data corruption or configuration fault. The condition becomes more visible as retention increases and scheduled reports overlap with normal orchestrator activity.

## Workaround
1. Reduce the flow-history retention window to 3 to 5 days so the reporting job operates on a smaller dataset. Apply the change from the orchestrator and commit it.
2. If the full retention period must remain in place, split reporting into narrower 24-hour jobs instead of broader multi-day jobs so each execution handles fewer rows.
3. Schedule report generation during a low-change maintenance window to reduce contention with policy pushes and other orchestrator tasks.
4. After the change, rerun the scheduled report and confirm that job runtime returns to the expected 3 to 4 minute range and that CPU remains below the prior peak.

```text
reporting flow-history retention 5d
commit
```

## Resolution
No software fix is required for this issue in 3.3. Prevent recurrence by keeping flow-history retention within 3 to 5 days where possible, or by reducing report scope to smaller time windows. If long retention is operationally required, schedule reports during low-activity periods so they do not compete with policy updates and other CPU-intensive orchestrator tasks.
