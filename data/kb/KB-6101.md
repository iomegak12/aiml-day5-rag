# KB-6101: HX-5000 7.2 SFP28 link drops with DOM bias current spike and remote LOS alarms

## Summary
On Helix HX-5000 systems running release 7.2, certain 25G ports using SFP28 optics can flap under steady traffic with a remote loss-of-signal indication. The issue is associated with a transient DOM bias current spike immediately before link loss, and it is fixed in release 7.3.

## Symptoms
Customers typically report that a 25G Ethernet port comes up normally, carries traffic for several minutes, then drops and recovers repeatedly at intervals of about 8 to 12 minutes. The far-end device reports LOS within 1 second of the local transition, while the local switch may show the interface as operationally down and then back up without a physical reseat of the optic.

On affected ports, `show interfaces transceiver detail` commonly shows a stable bias current near 6.1 mA during normal operation, followed by a sudden increase to approximately 11.4 mA immediately before the link loss. The optic usually remains seated and powered, and the behavior is reproducible only on release 7.2 with specific SFP28 modules.

## Diagnosis
1. 1. Run `show version` and confirm the switch is running Helix HX-5000 release 7.2. This issue is limited to 7.2 and is fixed in 7.3.
2. 2. Run `show interfaces transceiver detail ethernet 1/1` on the affected port and compare multiple samples over 10 to 15 minutes. Look for a bias current jump from about 6.1 mA to about 11.4 mA immediately before the interface drops.
3. 3. Run `show interfaces status ethernet 1/1` and confirm the port transitions between up and down without a physical reseat event or administrative shutdown.
4. 4. Check the remote endpoint logs for LOS asserted within 1 second of the local flap. A matching LOS on the far end confirms the optical path is being torn down rather than a protocol-only event.
5. 5. Run `show logging last 100` and look for `%TRANSCEIVER-4-LOS` entries on the affected interface with timestamps aligned to the flap interval.

## Root cause
In release 7.2, the optical polling path can latch an incorrect DOM snapshot when the module temperature changes by more than 7 C within a 30-second sampling window. When that stale snapshot is evaluated, the switch misinterprets the bias current excursion as a low-power condition and clears the SerDes lane.

That lane reset produces a transient loss-of-signal event even though the optic remains inserted and powered. The result is a periodic link drop with remote LOS alarms, most often seen under steady traffic where the module temperature oscillates around the threshold.

## Workaround
1. Reduce DOM polling activity on the affected interface so the switch samples the module less frequently during normal operation. Use the interface-level transceiver monitoring command to extend the interval to 120 seconds.
2. Keep the optic below 50 C case temperature if possible. Improve airflow, verify adjacent port loading, and remove any obstructions that increase local heating around the module cage.
3. If the port continues to flap under load, move the optic to a port running a later release or replace the module with one that shows a stable bias current profile during extended monitoring.
4. After applying the workaround, monitor the interface for at least 30 minutes and confirm that bias current remains near its baseline value and that no further LOS alarms occur.

```text
configure terminal
interface ethernet 1/1
transceiver monitoring interval 120
```

## Resolution
The defect is fixed in release 7.3. In that release, the DOM sampling logic validates consecutive readings before acting on bias current excursions, which prevents the false low-power condition and the resulting LOS event.
